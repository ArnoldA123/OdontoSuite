## 6. Decisiones técnicas

### 6.1 `updateOrCreate` por `code` (no por `id`)

Razón: idempotencia. `migrate:fresh --seed` regenera IDs, pero los `code` (SC-LIM-01, cash, etc.) son estables. Si re-ejecutamos el seeder, no duplica filas, solo actualiza los campos que cambiaron.

### 6.2 Columna `is_system` en migration separada (no en la original)

Razón: la migration original (`2025_10_24_202521_create_payment_methods_table.php`) es histórica y no debe tocarse. Una migration aditiva (`add_is_system`) es la práctica estándar para cambios no-rompedores. Reversible con `php artisan migrate:rollback`.

### 6.3 `useRouter` desde `vue-router` (no desde composable local)

Pitfall evitado: mi primer patch importó `useRouter` desde `@/composables/useRouter` (que no existe). Lo corregí a `from 'vue-router'`, que es el patrón canónico del proyecto (verificado en `CalendarPage.vue`, `LoginPage.vue`, `DashboardPage.vue`, etc.). `useRouter` global es la práctica del proyecto; no wrapper local.

### 6.4 Sin `EmptyState` import bug (pitfall #29e-2)

Verificado antes de usar `EmptyState.vue` en `OpenCashModal`:
- `grep "from 'vue'" resources/js/components/ui/EmptyState.vue` → línea 66 con `import { computed } from 'vue'` ✓
- No importaba `computed` accidentalmente sin el import de vue (que era el bug del Sprint 0 del plan #5).

## 7. Riesgos restantes (debitados a futuros sprints)

1. **Composición química de las comisiones** (3.50% tarjeta crédito) está hardcodeada en el seeder. Sprint 2 lo hará editable desde la UI admin.
2. **`is_system` solo bloquea visualmente** (en el futuro, la UI admin no mostrará "Eliminar" para métodos del sistema). Sprint 2 lo hará enforcement backend.
3. **No hay jerarquía de sucursales** (parent_branch_id). Out of scope (ver §8 del plan).
4. **El modal de payment no tiene empty state como tal** (solo un mensaje `<p class="text-amber-600">`). Suficiente para v1, Sprint 4 lo puede mejorar a un `<EmptyState>` real con CTA.
