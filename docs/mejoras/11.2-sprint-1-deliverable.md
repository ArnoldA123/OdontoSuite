## 1. Resumen

Sprint que entrega el **CRUD admin de sucursales** (`/settings/branches`) para que el rol `administrador` pueda crear/editar/desactivar sedes desde la UI, en lugar de depender de SQL o `tinker`. Tambien incluye el backend fixes del `BranchController` que estaban bloqueando el CRUD (no aceptaba `code/city/country`).

## 6. Decisiones técnicas

### 6.1 Endpoint público `/branches/active` separado del admin

**Problema detectado**: el `apiResource('branches')` está detrás de `role:administrador`, pero el `OpenCashModal` (usado por recepcionistas y finanzas) necesitaba listar sucursales. Si movía el GET al apiResource, los recepcionistas no podrian abrir caja.

**Solución**: ruta fija `GET /api/branches/active` (sin role gate) para el dropdown publico, `apiResource` queda con `role:administrador` para el CRUD admin. **Pattern L del skill** (route ordering): el segmento fijo `active` se registra antes del `{branch}` del resource, evitando shadowing.

**Aprendizaje reusable**: para listas "lookup" que un usuario no-admin necesita ver (dropdowns), exponerlas en endpoint dedicado (`/resource/active`) en vez de compartir con el CRUD admin. Mismo patron aplicara a `/payment-methods/active` en Sprint 2.

### 6.2 `address` y `state` con default string vacío

La migration original define `address` y `state` como `text`/`string` NOT NULL sin default. Tres opciones:
- A. Migration aditiva para hacerlos nullable (correcto a largo plazo, scope creep)
- B. Forzar string vacío en el controller si no se envian (pragmático, funciona)
- C. UI forza al usuario a escribir dirección (mala UX, address opcional es razonable)

**Elegí B** para este sprint. La opción A va a un sprint futuro de "schema cleanup". Documentado en §7.

### 6.3 `useBranches` acepta dos formatos de respuesta

El controller actual devuelve `{ data: [...] }` sin paginar. Si en el futuro se agrega paginación, Laravel devolvería `{ data: { data: [...], meta: {} } }`. El composable acepta ambos formatos para no romperse cuando alguien cambie el controller. Mismo patrón que `useProcedureCatalog`.

### 6.4 `getBranches` con `buildQuery` reutilizable

Patrón copiado de `useProcedureCatalog.js`. Centraliza la lógica de `URLSearchParams` para que agregar un filtro nuevo sea 1 línea.

### 6.5 Icono `BuildingOfficeIcon` como SVG inline

Mismo patrón que `CogIcon`, `ChartIcon` en `AppLayout.vue`. Evita agregar un import de `@heroicons` por cada icono nuevo y mantiene el bundle pequeño. El SVG es de 1 path simple, no justifica un import externo.

### 6.6 Modal de confirm con `<UiModal>` en vez de `useConfirm`

Consideré usar el composable `useConfirm` (singleton + Promise), pero el flujo de activar/desactivar tiene **2 modales diferentes** (uno para desactivar, otro para activar) y quería textos distintos. Dos `<UiModal>` locales son más legibles que parametrizar uno solo. Si en el futuro se agregan más acciones destructivas, vale refactorizar al singleton.

## 7. Deuda técnica debitada a futuros sprints

1. **Schema de `branches`**: `address` y `state` deberian ser nullable. Migration aditiva `2026_06_15_xxx_make_address_state_nullable_on_branches.php` con `->change()`. Out of scope de Sprint 1.
2. **No hay jerarquia de sucursales** (parent_branch_id). Out of scope (ver §8 del plan).
3. **`getBranches` no usa paginacion**: si la lista crece a 50+ sedes, el dropdown y la UI se ponen lentos. Out de scope, queda para cuando se justifique.
4. **No hay UI de jerarquia de usuarios por sede** (un usuario asignado a una sede solo ve data de esa sede). Eso es el plan multi-tenant original, parcialmente implementado.
5. **No se borra realmente, se desactiva**: por diseño (preservar auditoría). El botón "Eliminar" no existe en la UI; si el admin lo pide, hay que agregar flow con confirm adicional y check de FK.
